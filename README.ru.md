# Placitum cookie

[English](README.md) · Русский

Инспектор куки Placitum. Выдаёт клиенту подписанную куку, снимает её, пишет её значение в живой
набор и рассказывает об этом соседям. Сам ничего не проверяет и никого не блокирует: по выданной
куке решают другие — локальный слой на узле, действия соседей, счётчик.

Проще всего это видно на рекламном трафике. Клиент приходит по ссылке с `utm_source=yandex-direct`;
инспектор кладёт ему подписанную куку со значением-источником, пишет куку в динамический набор и ставит на
запись маркер `src:yandex-direct`. Кампания видна в журнале без единого похода в приложение, а узел
узнаёт клиента по набору — без шины и без инспектора.

```
модуль ──► waf.req.cookie ──► cookie ──► allow + Set-Cookie
                                 │
                                 ├── состояние куки: absent | present | invalid | expired
                                 ├── запись значения в динамический набор
                                 └── сигналы соседям: маркер, баллы
```

## Что нужно знать

- **Вердикт у него один — `allow`.** Баллы на маршруте он двигает сигналом `score`, которую исполняет
  модуль. Собственные сбои — `verdict: error` с кодом `COOKIE_*`, а не тихий `allow`: `allow` прятал
  бы невыданную куку.
- **Работает на обеих фазах.** На фазе запроса кука выставляется до апстрима, её видит и приложение. На
  фазе ответа известен код ответа, так что тому, кому апстрим ответил 404, куку можно не выдавать.
  Заголовки запроса на фазе ответа берутся из копии запроса: `Cookie` присылает клиент, а не апстрим.
- **Подпись по умолчанию.** Куку, по которой установка принимает решения, без подписи набирают вручную
  в консоли браузера. Подобранное значение — состояние `invalid`, а не «куки нет».
- **Маршрут обязан копировать заголовки.** Без них куку читать не из чего, и ответ — `error` с
  `COOKIE_HEADERS_UNAVAILABLE`. Считать это «куки нет» значило бы выдавать новую куку каждому на
  каждом запросе.

## Маршрут

```nginx
waf_inspector cookie subject=waf.req.cookie;

location / {
    waf_inspect request cookie wave=1 timeout=20ms;
    waf_capture request headers args;
    waf_cookie_defaults secure=on http_only=on same_site=Lax;
}
```

`args` нужен, если значение берётся из строки запроса (`value.from: $arg_utm_source`). Атрибуты
`secure`, `http_only` и `same_site` ставит `waf_cookie_defaults` маршрута, а не профиль: присланное с
провода модуль разбирает и выбрасывает. `Domain` модуль не ставит, кука остаётся host-only.

## Профиль

Профили приходят от контроллера поколением; в образе лежит пустой `default`. Маршрут, который
называет профиль, которого у инспектора нет, получает `error` с `COOKIE_UNKNOWN_PROFILE`.

```yaml
mode: enforce

cookies:                 # объявления: что это за кука
  - name: waf_src
    path: /              # умолчание /
    max_age: 30d         # нет — кука сессии
    renew_after: 7d      # возраст, после которого состояние — expired
    sign: hmac           # hmac (умолчание) | none
    value:
      from: $arg_utm_source  # операнд: $arg_, $http_, $cookie_, $waf_request_args.<имя>
      default: direct        # значение, если в запросе нет; одно — постоянное значение
      random: 0              # уникальный номер в байтах (умолчание 8); один — это и есть значение (uid)
      max_len: 64            # предел значения; длиннее — обрезается
  - name: uid
    max_age: 365d
    value: { random: 8 }     # свой номер каждому клиенту: 16 шестнадцатеричных знаков

rules:
  - name: first-touch    # имя живёт в журнале и аудите
    phase: request       # request | response; пусто — обе
    on: absent           # состояние куки на входе; пусто — любое
    match:               # должны сойтись все заданные поля; пусто — любой запрос
      path_prefix: /catalog
      methods: [GET]
    issue: waf_src       # операция: выдать
    actions:
      - do: mark
        marker: "src:{value}" # подстановки: {value}, {name}, {<имя куки>}
      - list: ads_clients     # запись в динамический набор
        write: cookie         # value | cookie | addr | net | net_all | asn
        ttl: 30d
        code: COOKIE_ADS

  - name: forged         # подпись не сошлась: куку подобрали
    on: invalid
    cookie: waf_src
    actions:
      - { do: score, value: 20, code: COOKIE_FORGED }

  - name: from-google    # значение предъявленной куки — одно из названных
    cookie: waf_src
    tags: [google]         # not_tags — ни одна из названных
    actions:
      - { do: mark, marker: "src:{value}" }

  - name: partner        # значение — в статическом списке: он приходит с поколением
    on: present
    cookie: waf_src
    listed: { list: partners, op: in, static: true }
    actions:
      - { do: mark, marker: "partner:{value}" }

  - name: sign-out       # номер клиента уходит в динамический список...
    on: present
    cookie: uid
    match: { path_prefix: "/logout" }
    actions:
      - { list: revoked, write: value, ttl: 30d }

  - name: revoked        # ...и кука с этим номером снимается, когда её предъявят снова
    on: present
    cookie: uid
    listed: { list: revoked, op: in }   # op: in | not_in; hash: md5 у хешированного списка
    drop: uid

  - name: logout
    match: { path_prefix: "/logout" }
    drop: waf_src        # операция: снять
    actions:
      - { list: ads_clients, write: cookie, op: remove }
```

### Состояния и операции

| `on` | Когда |
| --- | --- |
| `absent` | куки с таким именем клиент не прислал |
| `present` | кука есть, и подпись сошлась либо подписи не просили |
| `invalid` | кука есть, но подпись не сошлась, форма испорчена или время выдачи в будущем |
| `expired` | кука своя и целая, но старше `renew_after` |

Операций две, `issue` и `drop`, и правило делает одну из них. `on: absent` вместе с `issue` —
«первое касание»: кука достаётся только тому, у кого её нет. Правило без `on:` — «последнее
касание»: значение перезаписывается на каждом совпавшем запросе.

`tags: [google, yandex]` сужает правило по значению: оно срабатывает, когда значение предъявленной
куки — одно из названных (`not_tags` — ни одно из). Значение есть только у существующей куки
(`present`, `expired`), поэтому с `on: absent` и `on: invalid` такое правило не грузится. Значение
неподписанной куки выбирает клиент, так что решать по нему стоит только при `sign: hmac`.

`listed` ищет в списке значение куки — то самое, что кладёт туда `write: value`. Динамический список
инспектор держит зеркалом по протоколу keeper из внутреннего Redis. Статический (`static: true`) только
сравнивают, и приходит он с поколением: манифест называет его sha256 тела, инспектор читает тело из
внутреннего Redis (`waf.blob.<hex>`), сверяет хеш и кладёт рядом с профилями
(`profiles/.lists/<имя>.txt`, по значению в строке). Профиль, статического списка которого нет, не
грузится. При `hash: md5` значение перед поиском хешируется. Нет значения или динамический список ещё не
пришёл в зеркало — `in` ложно, `not_in` верно: отсутствие данных никогда не превращается в совпадение,
а событие `kind=inspector` отмечает такой список в `notes`.

Правило сужает только то, что в нём самом: `on`, `tags` или `not_tags`, `listed`, `phase`, `status`
(коды ответа, при `phase: response`) и `match` (`path_prefix`, `methods`, `suffixes`, `static`).
Условий у профиля куки нет: профиль с `conditions`, `if` или `unless` не грузится — выбросить их молча
значило бы расширить правила.

Правила накопительные: срабатывают все совпавшие, действия складываются в порядке строк. Судьба самой
куки порядком не решается: **снятие сильнее выдачи**, и правило выхода не проиграет правилу
посадочной страницы, стоящему ниже.

### Значение и подпись

```
<значение>[.<время>.<подпись>]
<значение>~<номер>[.<время>.<подпись>]   значение с номером, если так просит профиль, написанный руками
```

Значение — то, ради чего куку заводят: клиент, источник перехода, кампания. Оно одно из трёх:
`value.random` без остального — уникальный номер (uid), у каждого клиента свой; `value.default` без
остального — постоянное значение; `value.from` — переменная запроса, а `value.default` при ней —
запасное, когда в запросе пусто. Клиенту, у которого в запросе нет ни того ни другого, кука не
выдаётся, а событие `kind=inspector` называет такую куку в `no_value`. Правила сравнивают значение
(`tags`, `listed`), в маркер оно подставляется как `{value}`, `write: value` кладёт его в список. Алфавит
у него узкий: всё, что не `[A-Za-z0-9_-]`, становится подчёркиванием, и значение режется по `max_len`.
При значении с номером значение — часть до `~`. Строка целиком, со временем и подписью, — то, что
кладёт в список `write: cookie`.

Маркер — строка с подстановками в фигурных скобках из кук запроса: `{value}` — значение куки правила,
`{name}` — её имя, `{<имя>}` — значение любой куки профиля, так что `client_{uid}_{value}` становится
`client_a1b2c3_google`. Остальная строка остаётся как есть.
Подстановка куки, которой в запросе нет, снимает маркер целиком, а событие `kind=inspector` называет
его в `markers_dropped`. Профиль, маркер которого называет необъявленную куку или оставляет скобку
без пары, не грузится; у правила перегрузки своей куки нет, и куку там называют по имени. На `absent`
и `invalid` значения у куки правила нет, поэтому `{value}` там отвергается — если только правило не
выдаёт эту куку само.

Ключ берётся из `WAF_COOKIE_SECRET_FILE` или `WAF_COOKIE_SECRET`, не короче 16 байт, один на все
копии. На куку он разводится её именем, поэтому подпись одной куки не подходит другой. Без ключа
профиль с `sign: hmac` отвечает `error` с `COOKIE_SECRET_MISSING`, а не выдаёт неподписанные куки
молча. Время выдачи живёт в подписанной половине, поэтому `renew_after` и состояние `expired` требуют
`sign: hmac`.

### Запись в наборы

Действие может быть записью, а не сигналом: `list` с `ttl` (и `write`, `op`, `cookie`, `code`), без `to`
и `do`. Пишут только в динамический список. У `write` четыре вида, общих для всех отправителей, и два
своих:

| `write` | Что уходит в набор |
| --- | --- |
| `addr` | адрес клиента (умолчание) |
| `net` | эффективный анонс, самый узкий |
| `net_all` | все анонсы, накрывающие адрес, включая более широкие |
| `asn` | автономная система целиком |
| `value` | значение куки — то, что сверяет `listed` |
| `cookie` | строка куки целиком: значение, время и подпись — выданной на этом запросе либо предъявленной клиентом |

`cookie:` называет куку у обоих; без него запись берёт куку правила, а правило перегрузки, у которого
её нет, называет куку само. `write: value` наполняет списки, которые проверяют правила этого же
инспектора. Под `write: cookie` обычно и заводят набор на узле: `type=string`, почти всегда с
`hash=md5`, чтобы значения куки не лежали в разделяемой памяти открытым текстом. `op: remove` снимает
запись. Анонсы и
системы даёт справочник сетей (`WAF_COOKIE_GEO_ADDR`) в бюджете сообщения; молчащий справочник сетей — `error` с
`COOKIE_GEO_UNAVAILABLE`.

## Коды причин

| Код | Что значит |
| --- | --- |
| `COOKIE_OK` | правила посчитаны |
| `COOKIE_IDLE` | не своя фаза (кадры WebSocket) |
| `COOKIE_PROFILE_OFF` | у профиля `mode: off` |
| `COOKIE_UNKNOWN_PROFILE` | маршрут называет профиль, которого у инспектора нет |
| `COOKIE_HEADERS_UNAVAILABLE` | маршрут не копирует заголовки запроса |
| `COOKIE_STORE_ERROR` | буфер не отдал объект, который лежал |
| `COOKIE_SECRET_MISSING` | кука подписывается, а ключа у процесса нет |
| `COOKIE_ISSUE_FAILED` | значение не собралось: длиннее предела, случайное не прочиталось |
| `COOKIE_GEO_UNAVAILABLE` | строка пишет сеть или систему, а справочник сетей молчит |
| `COOKIE_QUEUE_LIMIT`, `COOKIE_DEADLINE_EXCEEDED` | перегрузка: очередь полна или бюджет вышел |

Что нужно рядом и все настройки — в [INSTALL.ru.md](INSTALL.ru.md).
