# Инспектор куки

Выдаёт клиенту куку, снимает её и рассказывает об этом соседям — действиями канала
`docs/inspector-actions.md` платформы. Ничего не проверяет и никого не
блокирует: вердикт всегда `allow`. Решают по выданной куке уже другие — локальный слой на краю,
автодействия соседей, счётчик.

Зачем это нужно, проще всего видно на рекламном трафике. Клиент приходит по ссылке с
`utm_source=yandex-direct`; инспектор кладёт ему подписанную куку с меткой источника, пишет её
значение в живой набор и ставит на запись маркер `src:yandex-direct`. Дальше кампания видна в
журнале без единого похода в приложение, а край узнаёт этого клиента по
`waf_local_check <набор> $waf_request_cookies.waf_src` — без шины и без инспектора.

Отсюда два свойства, которых нет у проверяющих инспекторов:

- **Вердикта, кроме `allow`, у него нет.** Вклад в счёт нулевой; очки на маршруте он двигает
  просьбой `score`, которую исполняет модуль. Собственные сбои — битое сообщение, чужая версия
  схемы, перегрузка, паника, обменник без заголовков, отсутствующий ключ подписи — это
  `verdict: error` с машинным кодом (`COOKIE_*`). `allow` на них прятал бы поломку: кука не
  выдана, а ответ выглядит годным.
- **Работает на обеих фазах.** На фазе запроса кука ставится до апстрима — её увидит и само
  приложение в своём же ответе. На фазе ответа — после, и там виден код ответа (`status:`), то
  есть можно не выдавать куку тому, кому апстрим ответил 404. Заголовки запроса на поздней фазе
  берутся из `request_store`: `Cookie` предъявляет клиент, а не апстрим.

## Что нужно от маршрута

```nginx
waf_inspector cookie subject=waf.req.cookie;

location / {
    waf_inspect cookie wave=1 timeout=20ms;
    waf_capture request headers args;
    waf_cookie_defaults secure=on http_only=on same_site=Lax;
}
```

`waf_capture request headers` обязателен: `needs` инспектора -- это и есть снимок маршрута, и без
него `Cookie` читать не по чему, а инспектор отвечает `error` с `COOKIE_HEADERS_UNAVAILABLE`.
Молчаливое «куки нет» означало бы новую куку каждому и на каждом запросе. `args` нужен, если
значение берётся из строки запроса (`value.from: $arg_utm_source`).

Атрибуты `secure`, `http_only` и `same_site` ставит `waf_cookie_defaults` маршрута, а не профиль:
присланное с провода модуль разбирает и выбрасывает. `Domain` модуль не ставит вовсе — кука
остаётся host-only, привязанной к текущему `server_name`.

## Профили

Каталог `WAF_COOKIE_PROFILES` (по умолчанию `./profiles`), один файл `<имя>.yaml` на профиль.
Имя называет `profile=` в реестре инспекторов; имени, которого нет среди загруженных, отвечает
`verdict: error` с `COOKIE_UNKNOWN_PROFILE` — чужая кука с чужим сроком и чужой меткой не тише
своей, она просто чужая.

Второй путь — раскатка контроллером: панель (раздел `/cookie`) держит профили в `cookie_profiles`,
кнопка «Разослать» кладёт манифест в KV `WAF_DESIRED`, ключ `policy/cookie`
(`docs/inspector-config-distribution.md` платформы).
`internal/desired` раскладывает поколение в `WAF_COOKIE_DATA` (по умолчанию `<профили>.applied`)
плоским каталогом `<имя>.yaml` и переключает загрузчик на него; битое поколение не применяется и
виден `apply_failed` в пульсе.

```yaml
mode: enforce            # печатает контроллер; включён ли инспектор -- вызов на маршруте

cookies:                 # объявления: что это за кука
  - name: waf_src
    path: /              # умолчание /
    max_age: 30d         # нет -- кука сессии
    renew_after: 7d      # возраст, после которого состояние -- expired
    sign: hmac           # hmac (умолчание) | none
    value:
      from: $arg_utm_source  # операнд: $arg_, $http_, $cookie_, $waf_request_args.<имя>
      default: direct        # источника нет -- эта метка
      random: 8              # + случайный хвост, байт; 0 -- без него
      max_len: 64            # предел метки до сборки значения

conditions:              # именованные условия; те же, что у инспектора действий
  - name: from_ads
    any:
      - value: $arg_utm_source
        op: ne
        text: ""

rules:
  - name: first-touch    # имя живёт в логе и аудите, на провод не едет
    phase: request       # request | response; пусто -- обе
    on: absent           # состояние куки на входе; пусто -- любое
    if: from_ads         # условие профиля; unless -- наоборот
    match:               # признаки запроса, как у инспектора действий
      methods: [GET]
    issue: waf_src       # операция: выдать
    actions:
      - do: mark
        marker: "src:{tag}"   # подстановки: {tag}, {value}, {name}
      - list: ads_clients     # запись в живой набор
        write: cookie         # addr | net | net_all | asn | cookie
        ttl: 30d
        code: COOKIE_ADS

  - name: forged         # подпись не сошлась -- клиенту куку подобрали
    on: invalid
    cookie: waf_src
    actions:
      - do: score
        value: 20
        code: COOKIE_FORGED

  - name: logout
    match: { path_prefix: "/logout" }
    drop: waf_src        # операция: снять
    actions:
      - list: ads_clients
        write: cookie
        op: remove       # add (умолчание) | remove
```

### Состояния и операции

Состояние куки на входе — это и есть весь словарь `on:`:

| `on` | Когда |
| --- | --- |
| `absent` | Куки с таким именем клиент не прислал |
| `present` | Кука есть, и подпись сошлась (либо подписи не просили) |
| `invalid` | Кука есть, но подпись не сошлась, испорчена форма или время выдачи в будущем |
| `expired` | Кука своя и целая, но выдана раньше, чем `renew_after` |

Операций две: `issue` и `drop`. Правило делает одно дело — `issue` и `drop` в одной строке
профиль не грузят. `on: absent` вместе с `issue` — это «первое касание»: кука достаётся только
тому, у кого её нет. Правило без `on:` — «последнее касание»: значение перезаписывается на каждом
совпавшем запросе. Разница между двумя моделями атрибуции видна в профиле, а не спрятана в
настройке с двумя значениями.

Правила накопительные, терминальных нет: срабатывают все совпавшие, действия складываются в
порядке строк. Спор за саму куку порядком не решается — **снятие сильнее выдачи**: правило выхода
не должно проигрывать правилу посадочной страницы из-за того, что стоит ниже.

### Значение и подпись

```
<метка>[~<случайное>][.<время>.<подпись>]
```

Метка — то, ради чего куку заводят: источник перехода, кампания, ветка теста. Она читается глазами
и уезжает в маркер записи, поэтому её алфавит узкий: всё, что не `[A-Za-z0-9_-]`, заменяется
подчёркиванием и режется по `max_len`. Значение куки едет в заголовок ответа, в живой набор и в
запись аудита, и байт, который клиент выбрал сам, не должен определять, чем это окажется на той
стороне.

Подпись стоит по умолчанию и не для красоты. Кука, по которой контур принимает решения — снять
инспектора, пропустить без проверки, посчитать своим, — без подписи набирается руками в консоли
браузера за секунду, и тогда автодействие по ней открывает дыру ровно того размера, на который ему
дали прав. Ключ берётся из `WAF_COOKIE_SECRET` (либо файла `WAF_COOKIE_SECRET_FILE`), не короче 16
байт, один на процесс и одинаковый у всех реплик; на куку он разводится её именем, поэтому подпись
одной не годится для другой. Ключа нет — профиль с `sign: hmac` отвечает `error` с
`COOKIE_SECRET_MISSING`, а не выдаёт неподписанную втихую.

Время выдачи живёт в подписанной половине, поэтому `renew_after` и состояние `expired` требуют
`sign: hmac`; правило с `on: expired` у неподписанной куки профиль не грузит — правило, которое не
срабатывает никогда, это опечатка, и находиться она должна на загрузке.

### Запись в наборы

Действие бывает не просьбой, а записью в живой набор — `list` + `ttl` (+ `write`, `op`, `code`),
без `to` и `do`. `write` — четыре вида, общие у всех отправителей
([modsec](https://github.com/exemt/placitum-modsec/blob/develop/docs/README.md#кого-писать-адрес-подсеть-автономная-система)), и
пятый, который есть только здесь:

| `write` | Что уезжает в набор |
| --- | --- |
| `addr` | Адрес клиента (умолчание) |
| `net` | Эффективный анонс, самый узкий |
| `net_all` | Все анонсы, накрывающие адрес, включая чужие широкие |
| `asn` | Состав системы целиком |
| `cookie` | Значение самой куки — выданной на этом запросе либо предъявленной клиентом |

`write: cookie` — то, ради чего инспектор вообще умеет писать наборы: набор под него заводится
`type=string`, почти всегда с `hash=md5` (значение куки в shm открытым текстом не лежит), и край
сверяет его быстрым путём, не спрашивая шину. Куки на запросе не оказалось — писать нечего, и это
обычный исход, а не ошибка.

`op: remove` снимает запись. Срока у снятия нет: запись либо есть, либо её больше нет.

Анонсы и состав системы инспектор спрашивает у кодера гео по gRPC (`WAF_COOKIE_GEO_ADDR`)
синхронно, в бюджете сообщения, и только для строк `net` / `net_all` / `asn`; кодер нужен и молчит
— ответ `verdict: error` с `COOKIE_GEO_UNAVAILABLE`, исход выбирает `waf_exception` маршрута.

### Условия

Условия — те же, что у инспектора действий, слово в слово: именованные блоки `all` / `any` со
сравнениями значений запроса с наборами и текстом, ссылки на другие условия, `if` и `unless` у
правила. Подробно — README инспектора действий, раздел «Условия».

## Коды причин

| Код | Что значит |
| --- | --- |
| `COOKIE_OK` | Ответ нормальный: правила посчитаны |
| `COOKIE_IDLE` | Не своя фаза (кадры WebSocket) |
| `COOKIE_PROFILE_OFF` | `mode: off` у профиля |
| `COOKIE_UNKNOWN_PROFILE` | `profile=` маршрута нет среди загруженных |
| `COOKIE_HEADERS_UNAVAILABLE` | Маршрут не снимает заголовки запроса, а профиль объявляет куки |
| `COOKIE_STORE_ERROR` | Обменник не отдал объект, который лежал |
| `COOKIE_SECRET_MISSING` | Кука подписывается, а ключа у процесса нет |
| `COOKIE_ISSUE_FAILED` | Значение не собралось: длиннее предела, случайное не прочиталось |
| `COOKIE_GEO_UNAVAILABLE` | Строка пишет подсеть или систему, а кодер молчит |
| `COOKIE_QUEUE_LIMIT`, `COOKIE_DEADLINE_EXCEEDED` | Перегрузка: очередь полна, бюджет вышел |

## Окружение

| Переменная | Умолчание | Что задаёт |
| --- | --- | --- |
| `NATS_URL` | `nats://127.0.0.1:4222` | Шина |
| `WAF_COOKIE_SUBJECT` | `waf.req.cookie` | Subject подписки |
| `WAF_COOKIE_NAME` | `cookie` | Имя себя в реплае и в пульсе |
| `WAF_COOKIE_PROFILES` | `./profiles` | Каталог профилей |
| `WAF_COOKIE_DATA` | `<профили>.applied` | Куда ложится поколение раскатки |
| `WAF_COOKIE_SECRET` | — | Ключ подписи, не короче 16 байт |
| `WAF_COOKIE_SECRET_FILE` | — | Файл с ключом; сильнее переменной |
| `WAF_COOKIE_GEO_ADDR` | — | Кодер гео для `write: net \| net_all \| asn` |
| `REDIS_URL` | из `inspector.conf` | Обменник: заголовки и строка запроса |
| `REDIS_INTERNAL_URL` | из `inspector.conf` | Внутренний Redis: зеркало наборов keeper |

Очередь, её поведение на переполнении и адреса Redis — в `inspector.conf`, форма общая для всех
инспекторов.

## Грабли

- **Две фазы — две выдачи.** Инспектор, вызванный на обеих фазах маршрута, отработает дважды.
  `phase:` у правила выдачи — не опция, а обязанность, если вызов стоит на обеих.
- **Пассивный не выдаёт.** `mode=passive` и `mode=vote` на вызове: модуль секцию `cookies` от
  такого ответа не применяет вовсе. Это правильно — пассивный на трафик не влияет, — но выглядит
  как «включил, а куки нет».
- **Host-only.** Кука с `shop.example.com` не видна на `www.example.com`: `Domain` модуль не
  ставит. Для атрибуции по поддоменам этого мало.
- **Кеш.** `Set-Cookie` на кешируемом ответе — классическая беда с CDN и `proxy_cache`: один
  клиент уносит куку другого. Статику из правил выдачи стоит исключать
  (`match: { static: true }` в правиле, которое ничего не выдаёт, либо `path_prefix` у того,
  которое выдаёт).
- **Длина.** Набор `type=string` держит запись до 256 байт, с `hash=md5` — 32; подписанное
  значение считается целиком, вместе с меткой, случайным хвостом, временем и подписью.
